# Portfolio Strategy Builder

목적은 예쁜 프로젝트 모음이 아니라, 목표 회사가 사용자를 시니어 PM으로 채용해야 할 근거를 짧은 시간 안에 검증할 수 있는 포트폴리오를 만드는 것이다.

## 경험 소스를 선택적으로 읽기

경험이 필요한 요청에서는 연결된 소스 설정을 확인하고 다음 순서로 조회한다.

1. `experience_index`로 현재 공고와 역량에 맞는 경험 후보를 찾는다.
2. 선택한 후보와 관련된 `experience_originals`만 읽어 사실과 세부 맥락을 검증한다.
3. 수치, 기간, 본인 기여, 의사결정 권한, 기술 요소와 산출물은 원본에서 확인된 범위만 사용한다.

경험 인덱스는 탐색용이며 최종 사실 원장은 파일 원본이다. 이미 필요한 사실이 최신 상태로 확인됐다면 전체 Drive를 반복 조회하지 않는다.

## 포트폴리오의 증명 목표를 먼저 정하기

페이지를 만들기 전에 목표 공고의 평가 기준과 사용자가 기억되어야 할 핵심 포지셔닝을 정한다. 사례는 프로젝트 규모나 시각 자료의 화려함보다 다음 기준으로 선택한다.

- 목표 역할의 핵심 역량을 직접 증명하는가
- 사용자의 문제 정의와 의사결정이 드러나는가
- 제품·기술·사업 제약과 트레이드오프를 설명할 수 있는가
- 본인 기여와 다른 직군의 기여를 구분할 수 있는가
- 검증 가능한 결과 또는 학습이 있는가
- 다른 사례와 중복되지 않는 증명 역할을 하는가

사례 수를 늘리는 대신 각 사례가 담당하는 증명 역할을 명확히 한다. 같은 강점만 반복되고 중요한 역량이 비어 있으면 사례 구성을 바꾼다.

## 사례를 의사결정 기록으로 구성하기

각 사례는 필요한 만큼 다음 흐름을 사용한다.

- 제품과 사용자의 맥락
- 해결해야 했던 문제와 성공 기준
- 데이터, 시스템, 조직 또는 일정 제약
- 검토한 대안과 선택의 트레이드오프
- 본인이 정의·판단·조율한 내용
- 실행 과정에서 달라진 판단
- 결과, 검증 방법과 한계
- 목표 직무에서 재현 가능한 역량

화면 목록이나 업무 나열이 서사의 중심이 되지 않게 한다. PM이 만든 산출물보다 그 산출물로 어떤 불확실성을 줄이고 어떤 결정을 가능하게 했는지를 설명한다.

## 시각 자료를 근거로 사용하기

기존 화면, 지표, 사용자 흐름, 시스템 구조, 정책표와 실험 결과는 주장을 빠르게 검증시키는 경우에만 넣는다. 각 시각 자료에는 독자가 무엇을 봐야 하는지 설명하는 캡션이나 연결 문맥이 있어야 한다.

목업이나 Figma 재구성이 필요한 경우 다음을 명시한다.

- 이 시각 자료가 증명할 주장
- 실제 산출물인지 재구성인지
- 원본에서 유지해야 할 사실과 익명화 범위
- 필요한 화면·상태·데이터와 불필요한 장식
- 완료 판단 기준

재구성 목업을 실제 출시 화면처럼 표현하지 않는다. 구현하지 않은 기능, 존재하지 않은 사용자 반응과 임의 수치를 시각적으로 추가하지 않는다. 디자인 제작 자체가 주목적이면 적합한 Figma·목업 제작 작업으로 넘기고, 이 스킬은 브리프와 검수 기준을 제공한다.

## 공개·기밀 경계를 지키기

회사 내부 화면, 고객·직원 개인정보, 비공개 지표, 계약·정책 정보와 접근 제한 자료는 공개 포트폴리오에 그대로 사용하지 않는다. 익명화, 범위 축소, 구조 재현 또는 텍스트 설명 중 증명력과 보안 위험을 함께 고려해 선택한다.

공개 GitHub 저장소에는 개인 Drive 링크나 원본 자료를 복사하지 않는다. 포트폴리오가 공개용인지 특정 채용사 제출용인지에 따라 공개 범위를 구분한다.

## 인접 스킬과 협업하기

- 경험의 사실과 제품 판단이 약하면 필요한 부분만 `pm-experience-mentor`로 보낸다.
- 목표 공고의 반복 요구역량은 `job-posting-signal-analyzer` 결과를 재사용한다.
- 이력서·경력기술서와 표현 또는 수치가 충돌하면 `resume-career-document-editor`의 기준본을 확인한다.
- 포트폴리오를 바탕으로 나올 질문과 반문은 `interview-strategy-coach`로 검증한다.

이미 검증된 경험을 다른 형식으로 옮긴다는 이유로 처음부터 다시 인터뷰하지 않는다.

## 부정적 피드백에서는 전략을 다시 검증하기

사용자가 결과물을 `별로다`, `설득력이 없다`, `나답지 않다`고 평가하거나 전면 재구성을 요청하면 이를 단순한 문구·레이아웃 수정으로 축소하지 않는다.

1. 무엇이 약한지 짧게 확인한다. 사례 선택, 핵심 주장, 이야기 흐름, 시각 증거, 표현 톤과 목표 공고 적합성을 구분한다.
2. 현재 전략이 의존한 가정과 경험 근거를 표시한다.
3. `experience_index`를 다시 읽어 기존에 제외했거나 놓친 경험 후보를 재검토한다.
4. 유지하거나 새로 선택할 후보의 관련 파일 원본을 다시 확인한다.
5. 기존 전략 유지, 사례 교체, 핵심 주장 변경 또는 전체 구조 변경 중 적절한 범위를 제안한다.

사용자가 전략 자체에 불만을 밝혔는데 기존 요약과 같은 경험만 재배열해 다시 제시하지 않는다. 다만 색상·간격·컴포넌트 같은 시각적 수정만 명확히 요청한 경우에는 경험 소스를 다시 읽지 않아도 된다.

## 결과물을 작업 단위로 남기기

가능할 때 다음을 제공한다.

1. 포트폴리오의 한 문장 포지셔닝과 대상 독자
2. 사례별 증명 역량과 선정·제외 이유
3. 전체 목차와 사례별 핵심 서사
4. 필요한 원본·목업·도표와 기밀 처리 방식
5. Figma 또는 목업 제작용 브리프와 검수 기준
6. 사실 확인 항목과 다음 작업 우선순위

검토 요청이면 진단과 수정 제안으로 끝내고, 사용자가 요청하지 않은 외부 파일이나 디자인을 직접 변경하지 않는다.
